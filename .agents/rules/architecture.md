# Rule: Architecture

**Applies to:** module structure, module dependencies, public APIs, abstraction boundaries, and backend choices.

## Module inventory

- **Existing and registered in `Source/meson.build`:** `Core`, `AppCore`, `Launch`.
- **Planned but not present:** `Math`, `Physics`, `Rendering`, `RHI`, `Window` (and future backend modules). Instructions below describe the intended boundaries; do not pretend these modules exist, and do not create them unless the task explicitly requires creating a new module.
- **Known inconsistency:** `Nix/package.nix` uses `pname = "TrafficEngine"` while the Meson project and all code use `Lumen`. This is documented repository state; do not attempt to rename it unless the task is explicitly that.

## Module boundaries

- A module's public surface lives under `Source/<Module>/Public/`; implementation lives under `Source/<Module>/Private/`.
- A module may depend only on modules listed in its `meson.build` `Depends` array, and only if that dependency is registered before it in `Source/meson.build` (see `rules/build.md`).
- **A module dependency must be intentional and represented by the build system.** Never solve an architectural problem by adding another module dependency: if two modules are coupled, first decide whether the coupling belongs behind an existing abstraction.
- Do not create arbitrary cross-module dependencies or circular dependencies; the dependency graph must remain a DAG.
- New modules follow the template generated by `Scripts/NewModule.py` and are wired into `Source/meson.build`.

## Layer responsibilities

- **Core** stays foundational and dependency-light: types, macros, and primitives that every other module may use. `Core` is currently the only module with an empty `Depends`.
- **RHI** (planned) defines the rendering hardware abstraction boundary. Generic rendering code must never depend on Vulkan/OpenGL implementation details, handles, enums, or calling conventions.
- **Rendering** (planned) depends on abstractions (RHI, Window), never on concrete graphics APIs.
- **Window** (planned) isolates platform-specific window/system code behind a platform abstraction.
- **Backends** — rendering backends (Vulkan, OpenGL, ...) and window/platform backends (X11, SDL, ...) — keep all backend-specific implementation isolated from generic engine code. Backend-specific functionality belongs in backend implementations, not in generic interfaces.

## Two independent backend dimensions

Window/platform backends and rendering backends are **separate abstraction dimensions**, not one concept:

```text
Window / platform backend:   X11, SDL, ...
Rendering backend:           OpenGL, Vulkan, ...
```

- The architecture must support any combination (SDL+Vulkan, SDL+OpenGL, X11+Vulkan, X11+OpenGL, ...) without generic engine code knowing which combination is in use.
- Do not couple the selection of a window backend to the selection of a rendering backend (no "SDL renderer" or "X11 Vulkan path" inside generic code). Selection happens at composition/wiring time, not inside the abstractions.
- Never leak backend-specific types, enums, handles, or calling conventions into generic RHI, Window, or engine interfaces unless explicitly documented and justified.

## Abstraction and API design

- Keep public APIs small and explicit. Document ownership, lifetime, thread-safety, and backend constraints (see `skills/api-design.md`).
- Avoid inappropriate abstraction: do not add layers that only forward calls without adding semantic value.
- Prefer value semantics and deterministic lifetimes where appropriate.
